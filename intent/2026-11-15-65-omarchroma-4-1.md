# Intent: Bump Omarchroma to 4.1.0, without Icons

## Problem

`nixarchy-omatheme` packages Omarchroma (the `omarchroma` flake input) as
`hyprchroma` and `omarchroma-plugin`. The input is pinned at 3.0.0
(`7048180`, September). Upstream is at 4.1.0 (`594bdf2`), 60 commits ahead,
and Nixarchy users miss its fixes and features:

- open GTK4/libadwaita apps restyle at a theme change, without a restart;
- Qt colours work on Qt 6.12 (we carry a local `perl` rewrite of
  `Panel.qml` for this, marked "drop once the input is >= 3.2.3");
- the desktop portal keeps sending the light/dark colour scheme after it is
  recycled, and a hung portal call no longer fails the sync;
- a Thunderbird target;
- frameworks are written in parallel, so theme changes apply faster;
- apps that keep the old theme are listed for restart, with Dismiss;
- security and robustness fixes (pidfd signalling, Python isolation,
  safer file writes).

The bump cannot be done by updating the lock. A test build against
`594bdf2` fails:

1. `pkgs/hyprchroma.nix` hooks our terminal, shell and editor renderers in
   before the `python3 - "$HYPRCHROMA_LIB/hyprchroma-state" "$STATUS_FILE"`
   line in `bin/hyprchroma`. The status update is still there
   (upstream `bin/hyprchroma:1555`), but is now called as
   `/usr/bin/python3 -I - ...`, so the exact marker no longer matches and
   the build stops with `hyprchroma status update marker was not found`.
2. Several `/usr/...` substitutions no longer match, and upstream now
   hard-codes paths our build does not rewrite, chiefly 17
   `/usr/bin/python3 -I` calls and shebangs. Some of these (and
   `/usr/bin/bwrap`, `/usr/share/pixmaps`) sit only in the installer or the
   Icons helper, which this task does not package.
3. `omarchroma-plugin` depends on `hyprchroma`, and `Panel.qml` grew by
   about 1,500 lines, so `pkgs/patches/omarchroma-panel.patch` very likely
   no longer applies.

Upstream also changed behaviour our module relies on:

4. **The theme hook is now asynchronous.** `share/hooks/hyprchroma`
   signals the running `hyprchromad` service with SIGUSR1 and returns at
   once: "Hooks after this one may run before it has finished." Today the
   sync, including our renderers, finishes inside the hook.
5. **Service hardening conflicts.** Our unit (`modules/nixos.nix:497-503`)
   sets `PrivateTmp`, `PrivateDevices`, `ProtectKernelTunables`,
   `ProtectKernelModules`, `ProtectControlGroups`, `ProtectHostname` and
   `ProtectClock`. Upstream's unit leaves them out on purpose: in a user
   service each needs a private mount namespace, from which the daemon
   cannot read other processes, "took every window for stale, and wrote
   beneath browsers it could not see were running". Upstream also adds
   memory, task and CPU limits our unit does not inherit.
6. **State files gain fields.** Settings gain `appsSaved`, `restartMode`
   (legacy `force` maps to confirm) and `staleDismissed`; the status file
   gains Thunderbird and Icons fields and original-profile records. The
   inspected changes are additive.
7. **Qt fallback icons.** `lib/sync-qt-kde-theme` now builds a hybrid
   `Omarchroma` icon theme with a Breeze fallback for Qt apps, separate
   from the Icons feature.
8. **The panel exposes excluded features.** Upstream `Panel.qml` has
   Icons, setup and uninstall controls.

## Proposed outcome

Observable by the owner:

- The `omarchroma` input points at 4.1.0, and `nix flake check` passes.
- Everything that works today still works after a theme switch: GTK, Qt/KDE,
  browsers, Electron apps, terminals, shell, Neovim and Vim (#63), the bar
  widget and panel, and palette capture/restore.
- The upstream gains above reach Nixarchy, where they apply to NixOS:
  - an open libadwaita app (for example Nautilus) restyles without a restart;
  - the Qt 6.12 shortcut in `pkgs/omarchroma-plugin.nix` is removed;
  - Thunderbird can be enabled as a target;
  - the restart and Dismiss list works, and never lists Neovim or Vim,
    which already follow the theme live.
- No packaged script calls a path that does not exist on NixOS.
- Existing users upgrade in place: saved settings, captured original
  palettes and our renderer status survive the bump, and rolling back to the
  previous generation still works with the newer state files.
- After a theme switch, our renderers (terminals, shell, editors) still run
  and palette capture still sees the new theme, whether the sync runs in the
  hook or in the service.
- The panel does not offer Icons, setup or uninstall controls that do
  nothing on NixOS.

Out of scope:

- the 4.0 Icons feature (themed icon packs from the AUR and
  `/usr/share/icons`); a later issue can port it;
- the Arch installer paths in `hyprchroma-setup` and the new
  `hyprchroma-uninstall` (sudo, AUR, `pacman`), which the NixOS module
  replaces.

## Affected users and systems

- `flake.nix` and `flake.lock` (the `omarchroma` input).
- `pkgs/hyprchroma.nix`, `pkgs/omarchroma-plugin.nix`,
  `pkgs/patches/omarchroma-panel.patch`.
- `modules/nixos.nix` if new targets, settings or runtime dependencies need
  wiring (Thunderbird, adw-gtk-theme, bwrap).
- `tests/`, the flake checks, `README.md` and `docs/target-matrix.md`.
- Every user of `programs.nixarchyThemeEngine`, including the Nixarchy ISO.
- After merge, the pin in `~/.config/nixos` and the owner's hosts p620 and
  Razer, for the runtime check. p510 only with the owner's OK.

## Constraints

- Must keep our Nix packaging approach: no AUR, no `pacman`, no writes
  outside the user's home at runtime.
- Must keep the renderers this repo adds (terminals, shell, Electron,
  editors) and the `hyprchroma terminals|shell|electron|editors`
  sub-commands.
- Must keep every service hardening setting that does not break the
  daemon; any setting removed is named and justified by a test on NixOS.
- Upstream code is third-party: read it before packaging, and keep its
  license and attribution.
- Builds and runtime checks run on p620 and Razer only.

## Open questions

1. **Thunderbird:** enabled by default like the other targets, or opt-in?
2. **Restart mode:** upstream's default `restartMode=off` keeps the list of
   stale apps, Dismiss and manual restart, but never closes apps on its own.
   Keep that default, or let the module set it?
3. **adw-gtk-theme:** upstream now offers it as its own dependency. Should
   the module install it when the GTK target is on?
4. **Icons:** is a follow-up issue for the Icons feature wanted, or drop it?
5. **Service hardening:** may the seven namespace settings listed in
   problem 5 be removed, if a test on NixOS shows they break stale-app
   detection, as upstream reports?
6. **Asynchronous hook:** is it acceptable that the theme picker returns
   before the sync finishes, as upstream now does?

## Owner decisions (at approval)

1. Thunderbird is on by default, like the other targets.
2. Keep upstream's default `restartMode=off`.
3. Install adw-gtk-theme when the GTK target is on.
4. Icons: open a follow-up issue.
5. The seven namespace settings may be removed only if a NixOS test shows
   they break stale-app detection.
6. The asynchronous hook is accepted, provided our renderers and palette
   capture are proven to run after a switch.
