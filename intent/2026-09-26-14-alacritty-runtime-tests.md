# Intent: Audit Alacritty bridge and add runtime test matrix

## Problem

The project has an Alacritty bridge alongside the Kitty, Foot, Ghostty, and
shell integrations, but the documented ownership and runtime behavior are not
fully consistent. The project also relies too heavily on manual host testing to
prove that a theme switch updates supported runtime targets without a rebuild.

## Proposed outcome

Alacritty's actual ownership, reload behavior, and Stylix interaction are clear
and accurate in the code and documentation. A small deterministic test matrix
proves the runtime renderer's theme-switch contract for supported targets,
including Alacritty's bridge boundary, without requiring a permanent change to
a user's NixOS configuration.

## Affected users and systems

- NixOS users using Stylix with Alacritty or other supported runtime targets.
- Nixarchy users without Stylix.
- The Hyprchroma renderer, NixOS/Home Manager module, documentation, and CI.
- Razer as the runtime validation host.

## Constraints

- Do not edit `/home/olafkfreund/.config/nixos`.
- Keep Stylix optional and preserve the no-Stylix Nixarchy installation path.
- Keep one writer per user configuration file and never write to the Nix store.
- Tests must be deterministic, isolated, and runnable in CI without a desktop.
- Preserve existing runtime reload and restart-required semantics.
- Follow the repository artifact approval gates before implementation.

## Open questions

- Should Alacritty receive a dedicated runtime target/status entry, or remain a
  bridge-only integration because its existing configuration is regenerated by
  the theme hook?
- Which target status transitions belong in the automated matrix versus the
  Razer host test?
